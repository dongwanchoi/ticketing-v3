# MVP contract semantics v0.2
Implement all OpenAPI0.2 paths, names and statuses. Public catalog includes only APPROVED rows (sale readiness gates booking, not discovery). q searches title case-insensitively. Seat details require login; seller/admin routes require exact role. Registration always BUYER, no self-selected roles. Trusted V3-only CLI provisions seller/admin for dev/test; role transitions and public seller onboarding remain deferred.
Server sessions rotate upon login; password hashing BCrypt, logout invalidates session, cookies HttpOnly and Secure in HTTPS. CSRF endpoint issues token; client refreshes token after login/logout. Consistent Error JSON on application and security failures. No client-supplied user ID or price accepted.
Seller creates owned venue and physical row/number seats; performance refers to owned venue. Sessions copy physical seats into per-session inventory, one uniform session price for MVP (grading deferred). Additional sessions do not mutate existing inventory. Sale is one row per performance; dates both null or end > start, all sessions share. Approval must precede hold/payment. Admin cannot review own performance. No edit/delete endpoints once inventory exists in this version; destructive mutation is deferred.
Hold creation accepts1..4 distinct physical seatIds for one session, server computes expiry=now+300s and total from session inventory. Conditional inventory updates and affected-row checks inside one transaction; stable seat ordering prevents deadlocks; rollback every seat if any conflict. Availability queries consider expired holds available, but reacquisition and cleanup must always compare old hold ownership. GET/release require hold owner. Release is idempotent for already released/expired holds; confirmed holds cannot be released. Expired confirmation fails and cannot overwrite new owner. No global active-hold quota is introduced without policy approval.
Idempotency keys scoped by authenticated user + operation, store request fingerprint; matching replay returns same result, payload mismatch409. Persist uniqueness in MySQL to handle concurrent requests. Payment outcome is simulation only; SUCCESS transaction atomically checks ownership/expiry/sale, books seats and creates unique reservation+payment. FAILURE stores failed payment only; no new reservation/booking. No retry with different key after a failure is implemented (409 POLICY_NOT_ENABLED); replay same key returns same failed result. Do not decide early release after failed payment: hold remains governed by existing TTL/explicit release only. Reservation history current user only. No cancellation/refund/resale endpoints.
Pending optional policies do not block approved purchase flow. Implementations may propose contract corrections to coordinator, never silently diverge.
