## 아키텍처·잠금·성능 기준선

`ReservationService.create/payable → PerformanceService.requireSale → ManagementRepository.find(id,true)`의 `FOR UPDATE`가 같은 공연의 다른 좌석/다른 회차까지 직렬화한다. 판매 상태/관리자 승인 변경과의 경쟁을 막는 보수적 gate이며 이번에는 잠금 전략을 바꾸지 않았다. 다른 공연은 다른 gate row를 사용한다. 정합성 테스트와 이 병목 관찰은 별개다.

제한된 로컬 측정: 실제 서로 다른 인증 사용자40명, 요청 동시성10, 매 배치40개의 서로 다른 좌석, 동일 공연1개 vs 공연4개 분산,3회씩. 가입/로그인/fixture 준비/해제는 측정 구간에서 제외. Next proxy→Spring→MySQL 응답 지연과 batch 요청률을 측정했다.

| Round | 동일 공연 요청/s | 동일 공연 p95 ms |4공연 분산 요청/s |4공연 p95 ms |
|---|---:|---:|---:|---:|
|1|97.76|125.19|176.07|76.47|
|2|98.86|117.16|144.50|92.50|
|3|110.10|103.46|252.53|50.32|

240개 요청 모두201. 별도 읽기 전용 MySQL 조회로 benchmark description에 속한 선점240건 전부 RELEASED, 해당 inventory200행 AVAILABLE을 확인했다. 원시 측정/제약/최종 상태: [JSON](qa-artifacts/2026-10-29-hold-benchmark.json).

측정 한계: executor cgroup4CPU/32GiB지만 전용 하드웨어 아님, 작은40샘플의 p95, warm JVM/DB, 고정 scenario 순서, 실제5분 만료 브라우저가 동시에 유휴 대기, 외부 latency 없음. JIT/cache/host scheduling을 통제하지 않았으므로 성능 차이를 잠금 하나의 인과 효과나 운영 TPS/p95 SLA로 주장하지 않는다. gate 병목과 일치하는 관찰일 뿐이다. 다음 단계는 더 긴 반복·순서 교차·DB wait 관찰이고, shared gate lock 또는 더 작은 잠금 범위는 판매/승인 경쟁·락 순서 정합성 회귀를 동반해 별도 검토한다. Redis/Kafka/MSA를 도입하지 않았다.

| 신규 회차만 검수, 기존 승인 회차 유지 | 기존 구매/진행 중 선점을 건드리지 않고 변경 검수 | 회차별 검수 상태·판매 조건·관리 화면 추가 필요 |
| 변경 시 공연 전체 재검수 | 승인 경계 단순 | 기존 회차 노출·진행 중 선점/결제·이미 확정 예매 영향이 커 세부 정책 선결 필요 |

재검수가 필요하다면 신규 회차만 별도 검수하는 대안을 우선 비교할 것을 권장하지만 **구현·확정하지 않았다**. 취소·환불·재판매·결제 재시도·공개 역할 전환·좌석 등급·사용자별 총 활성 선점 수·유료 인프라도 미확정으로 유지한다. 이번 복원은 전체 본인 선점을 보여 주는 읽기 기능이며 임의 quota를 도입하지 않는다.

활성 목록은 mount/수동 새로고침 기준이고 실시간 push는 아니다. 이전 탭/장치의 상태가 바뀌어도 결제/해제는 서버 재검증하며 잘못된 소유권·만료 확정을 막는다. 캐시·실시간 구독/운영 rate limit·브라우저 확대/스크린리더 전체 검사는 추후 필요에 따라 검토할 수 있다.
